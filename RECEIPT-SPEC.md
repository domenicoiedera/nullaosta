# RECEIPT-SPEC — the v0.1 format freeze (§3.0, BUILD-PLAN-OSS v2)

Status: FROZEN. Every hash, test and doc sits on this file. Do not change a
byte of it without a receipt-of-receipts discussion; v0.1 ships exactly this.
Amended 2026-10-20 with the verifier defects the v0.1 rehearsal surfaced: the
seal preimage binds content only, never the file's path, and `verify` never
trusts the receipt's own `gated` flag for the irreversible classes.

Product homepage claim (one honest line, also in README): v0.1's gate is
**advisorial at the call boundary** — an agent that never calls `check` is not
stopped by it. v0.1 governs the actions that go through the gate, and proves
what happened. The enforcing adapters (MCP server, browser drivers) are the
next increment.

## 0. The three roles, three keys (§3.3 — part of the format, not an afterthought)

| Role | Principal | Key | Holds nothing | Never holds |
|---|---|---|---|---|
| The agent | — | — | **any key at all** | the receipt key, the approver key |
| Executor / receipt-writer | `executor` in the config, e.g. `agent-receipt` | **receipt key** (seals receipts) | — | the approver key |
| Human approver | an identity in `allowed_signers`, e.g. `founder` | **approver key** (signs approvals) | — | the receipt key |

Enforcement, implemented (not documentation):

* the approver **key** is only ever read by `ssh-keygen` via the `approve`
  verb, run by the human; no nullaosta module reads its bytes;
* `approve` **refuses** (`exit 1`, branch `SELF-REFERENCE`) when the
  `--principal` handed to it equals the configured `executor`;
* gate and `verify` re-check cryptographically: an OPEN entry of a gated
  class must carry an approval whose **verification principal is inside
  `allowed_signers` AND is not the executor** (`verify` exit 1
  `TRUST-SPLIT-VIOLATION`; gate branch `NOT-AUTHORIZED`).

`allowed_signers` is the single trust anchor. It must contain (a) the approver
identity/identities and (b) the `executor` identity, so receipt seals can be
bound to the writer. It is supplied **from outside the repo** by the verifier
(see §6).

## 1. Receipt file

One file, JSON object, UTF-8, written **atomically** (temp file + `os.replace`)
by a single-writer process:

```json
{
  "nullaosta_receipt": {"v": 1},
  "executor": "agent-receipt",
  "entries": [
    { "seq": 0,
      "prev_hash": "00..00",
      "at": "2026-10-20T09:00:00+00:00",
      "action": {"action_class": "pay", "target": "https://shop.example.com/checkout",
                  "params_digest": "<sha256 hex of canonical params>",
                  "nonce": "<32 hex per attempt, generated by the gate>",
                  "issued_at": "2026-10-20T09:00:00+00:00"},
      "action_hash": "<sha256 hex of canonical action bytes, §2>",
      "gated": true,
      "decision": {"verdict": "OPEN", "branch": null, "reason": "approval verified for ac1..."},
      "approval": {"principal": "founder", "sig": "<SSHSIG, §4>"},
      "seal": {"covered": 1, "head": "<§5 head after 1 entry>", "sig": "<§5 SSHSIG>"}
    }
  ]
}
```

Field rules:

* `entries` is append-only; an existing entry is **never edited**. v0.1 rewrites
  the whole file on append (single writer, temp+rename); an externally
  truncated file is detected by the rules below and is NOT OK.
* `executor` is the receipt-writer principal. The writer cannot rename itself
  to escape the trust split: its seal signatures only validate if the verifier's
  `allowed_signers` contains the claimed name.
* `gated` is true for the irreversible classes (`pay`, `submit`, `delete`,
  `send`, `publish`) per policy. An OPEN entry with `gated: true` that has no
  `approval` object is invalid (exit 1, `NO-APPROVAL-ON-OPEN`) in `verify`.
  `verify` does NOT trust this flag: the irreversible classes are gated by
  definition, so an OPEN on one of them with `gated` absent or false is
  invalid too (exit 1, `GATED-CLASS-WITHOUT-APPROVAL`). This needs no policy
  file; the names are fixed in `policy.IRREVERSIBLE`.

## 2. Canonical action bytes (the thing the approval signs)

Deterministic serialisation, sorted keys, UTF-8, no insignificant whitespace
(`json.dumps(action, ensure_ascii=False, sort_keys=True, separators=(",", ":")).encode("utf-8")`)
of exactly

```python
{"action_class": <str>, "target": <str>, "params_digest": <str>,
 "nonce": <str>, "issued_at": <UTC ISO-8601, seconds precision, +00:00>}
```

* `action_hash = sha256(canonical action bytes)` — the value the approval signs.
* `params_digest = sha256(canonical params bytes)` where the raw `params`
  (arbitrary JSON object) is serialised the same deterministic way. The raw
  params are stored only in the pending-action file, never in the receipt;
  the receipt carries the digest.
* **nonce is generated per attempt by the gate** (`secrets.token_hex(16)`), so
  two identical actions never share an `action_hash`. This makes a captured
  approval unusable on any other attempt — including a re-run of the very same
  command seconds later (different nonce ⇒ different hash).
* timestamp format: `datetime.now(timezone.utc).isoformat(timespec="seconds")`
  (ends `+00:00`).

The pending-action file (`nullaosta-pending.json`, produced by `check` when a
gated action waits for a human) stores:

```python
{"nullaosta_action": {"v": 1},
 "action": <the action object above>,
 "params": <raw params>,          # so the human can read what they approve
 "action_hash": <hex>}
```

`check` re-derives `params_digest` and `action_hash` from this file at use
time; any mismatch is a usage error (exit 2), never accepted.

- Namespace `nullaosta-approval`; preimage `nullaosta-approval:v1:<action_hash>`
  (exact string, no trailing newline beyond none added).
- The approver signs with their own key, `ssh-keygen -Y sign -f <approver key>
  -n nullaosta-approval <preimage file>`; `approve` never receives the receipt
  key and never signs receipts.

## 4. Consumed-nonce ledger (single-use, anti-replay)

The ledger lives **inside the sealed chain** — it is not a parallel file the
writer could edit:

* every OPEN entry of a gated class **spends** the nonce recorded in its own
  `action.nonce`;
* before any OPEN, the gate scans the sealed receipt entries for the nonce and
  refuses if found (branch `SPENT`, exit 1);
* `verify` re-derives this independently: the same nonce must appear in the
  receipt file at most once across all entries; twice ⇒ exit 1
  (`SPENT-NONCE-REUSE`) — replay leaves exactly this fingerprint if the
  attacker re-appends it.

Blocked-as-pending approvals consume nothing.

Timeout: an approval older than `expire_seconds` (config, default 900) —
measured from the action's own `issued_at` — is refused, branch `EXPIRED`
(exit 1). An approver that never answers / is configured but cannot be reached
is branch `APPROVER-UNREACHABLE` (exit 1). No-approval-yet is `NO-APPROVAL`
(exit 1). **Every one of these is a decision verb exiting 1 (BLOCKED); the
gate never continues anyway.** Exit 2 is reserved for "could not decide"
(usage, unreadable config/policy) — also never an OPEN.

## 5. Per-append seal (seal cadence: no unsealed tail)

Every entry is sealed **as it is written**, and the seal signs the **entire
chain including that entry**:

* `entry_hash(i) = sha256(canonical entry bytes)`, where canonical entry bytes
  = the entry JSON object serialised with `seal` **removed** (seq and
  prev_hash are keepers here, unlike the action dict — they participate in the
  hash: rewriting history forces every downstream hash to change).
* `prev_hash(0) = 64 hex zeros`; `prev_hash(i) = entry_hash(i-1)`; `seq` is
  0-based.
* `head(n) = sha256("\n".join(entry_hash(0..n-1)))` — the chain head after n
  entries, computed exactly like the proven sibling shell.
* entry `seal` = `{"covered": n, "head": head(n), "sig": SSHSIG}` where the
  SSHSIG signs the preimage string
  `nullaosta-receipt:v1:<n>:<head(n)>` in namespace
  `nullaosta-receipt`, made with the **receipt key**. The preimage contains
  no path: the seal binds CONTENT ONLY (the head through entry `n`), so an
  offsite copy saved under a different filename verifies identically, while
  any change to the recorded bytes still breaks the preimage.
* timestamps (`at`, `issued_at`) are writer-asserted; `verify` does not
  check them against real time (freshness is measured only from the
  action's own `issued_at`, itself writer-asserted — see §4).
* the writer's crash window is between "entry computed" and "seal attached":
  because the file is written only after the seal exists (temp + rename), the
  only observable states are the previous complete state or the new complete
  state. A file whose **last** entry has no `seal`, or whose last seal does not
  re-verify, is **UNSEALED = NOT OK**: `verify` exits 1 with
  `UNSEALED-OR-TRUNCATED` (also the verdict for a byte-truncated, unparsable
  file). An unsealed file is never reported as clean.

## 6. `verify` — independent, third-party

Reads only (1) the receipt file and (2) an `allowed_signers` file the verifier
supplies from outside the audited system. Exits:

* **0** — chain sound, every seal validates, every OPEN-gated entry carries a
  valid approval signed by a principal inside `allowed_signers`, not the
  executor, and no nonce spent twice; the seal binds content only, so the
  receipt may have been copied or renamed before verification and the
  outcome is the same;
* **1** — ANY tamper or rule breach: file unparsable/truncated, structure
  broken, chain does not link, a seal missing/invalid/stale, an approval
  invalid or bound to the wrong hash, `SPENT-NONCE-REUSE`,
  `TRUST-SPLIT-VIOLATION`, `NO-APPROVAL-ON-OPEN`,
  `GATED-CLASS-WITHOUT-APPROVAL` (an OPEN on a permanently irreversible
  class recorded with the `gated` flag cleared), `UNSEALED-OR-TRUNCATED`;
* **2** — could not run at all (no ssh-keygen, unreadable anchor, usage).

This answers the evidence question, not the admission question: `0`
proves the receipts are intact and independently signed. It does not assert
that every action an agent ever took passed through the gate (the advisorial
boundary above).

## 7. Verbs and exit taxonomy

```
init       write nullaosta.json + policy.json           0 ok / 2 error
check      policy+gate decision; appends a receipt      0 OPEN / 1 BLOCKED / 2 could-not-decide
approve    human signs an action hash (approver key)    0 signed / 1 refused / 2 error
verify     independent third-party verification         0 ok / 1 tamper / 2 could-not-run
log        informational listing of receipts            0 readable / 2 unreadable
```

Library API (bound in `nullaosta/__init__.py` and `pyproject.toml` — the name
appears in exactly those two places): `decide()`, `seal()`, `verify()`.

## 8. Residual risks, stated (§3.3 honesty)

* The receipt-writer holds the receipt key, so it can *rewrite* history
  (drop entries, re-stamp, re-seal) — it cannot, however, **mint
  approvals**: those require the approver key, and every approval binds one
  nonce. Deleting the spend record of an approval and reusing that approval
  is therefore possible for the writer alone; an auditor who keeps an
  out-of-band copy of the receipt file detects the deletion against their
  copy.
* **The spent-approval ledger is scoped to ONE receipt file.** It stops all
  same-file reuse, but it is not a global registry: if the writer starts a
  fresh receipt file, a spent approval opens again (and the fresh file
  re-seals cleanly). The writer-rewrite boundary and this ledger scope are
  the same fact: anything the writer can do in one file can be done again
  in a new one. Anchor the chain head out of band (an auditor's own copy,
  or a place the writer cannot touch) to close both.
* Timestamps (`at`, `issued_at`) are writer-asserted and are not checked
  against real time by anything outside the receipt itself; `verify`'s
  only time use, the approval expiry, is measured from `issued_at`'s own
  claim.
* The gate is advisorial at the call boundary — see §0.
